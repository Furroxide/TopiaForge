# Public multiplayer activity bands

Activity is inactive until both `MONITOR_ACTIVITY_TOKEN` (at least 32 characters) and `MONITOR_SERVER_IDS` (whitespace-separated public signing-key hashes) are configured. Use a dedicated monitor token, never an administrative or deployment credential. Synthetic identities remain excluded.

Only public Internet sessions contribute. Invite-only and LAN sessions contribute neither sessions nor players, so subtracting public listings cannot reveal an invite-only population. Public hosts already supply their player estimate for browsing. Registration, descriptor changes and heartbeats coalesce a lease in a durable outbox; analytics failures never refuse hosting. A change from public to invite-only withdraws the previous public lease with a zero-count tombstone. Invite-only hosts without a previous public lease create no activity row.

Sixteen shards use stable public server IDs internally for idempotency. These are pseudonymous host identifiers, not anonymous data. Leases contain versions, expiry times and public player estimates, but no addresses, names, descriptors, candidates, invites, tokens or player identities. Leases expire with the host's ninety-second lifetime. Tombstones and expired rows are scheduled for cleanup 180 seconds after their last update. Alarm execution may occur later; expired rows are excluded from totals regardless of cleanup timing. Each outbox has at most three attempts within ninety seconds.

Every five minutes the collector reads all shards. A missing or unqualified result makes the whole sample unavailable. Fewer than five public sessions or ten public players suppresses both bands. Otherwise sessions round down to a multiple of five and players to a multiple of ten **before storage**. The released inclusive bands are that lower bound through four or nine above it. No exact totals are stored in snapshots or published. Slots are immutable; warmup lasts ninety seconds; release waits fifteen minutes from the last shard result. Snapshot retention is one day.

`GET /v1/monitor/activity` requires the separate bearer token and returns schema `topiaforge.activity/2`, `scope: "public"`, `sampledAt` (UTC seconds), `state` (`available`, `suppressed`, `unavailable`), `sessionsBand`, and `playersBand`. An available band has integer `min` and `max` endpoints; both are null for suppressed/unavailable data. Before any delayed snapshot, or if a mixed-version snapshot reply lacks schema version 2 or public scope, it returns 503. Wrong or absent credentials return 401. Public browsing and `/v1/status` are unchanged.

## Upgrade and production gate

Version 2 has separate outbox, lease, warmup and snapshot tables. Initialization removes the old combined tables rather than relabeling their rows. Shards reject unqualified legacy writes; the collector rejects legacy shard totals. New hosts discard legacy outboxes. A rolling upgrade may temporarily show unavailable activity; it must never fall back to version 1. Old deployed code is not made safe by a source change: retire old producer instances before reenabling monitor collection.

The status repository uses a new public-only table, removes old history and rejects subsequent legacy-table writes. Its ingest validator rejects version 1; both current and history APIs reconstruct only qualified bands; the history cache uses a new namespace. Its browser rejects legacy responses independently. Published bands are retained for ninety days. Never convert combined history into public history by rounding it.

Before production activation, deploy the status migration, Worker and assets, retire old Worker versions and purge the old history cache; deploy the producer; verify only version 2 is accepted and old current/history responses cannot return. Resume collection only after these checks. Ship and verify the public activity disclosure in all three hosting paths before production: CLI, launcher and native in-game Public HOST. The native note covers both starting a public game and opening an existing solo game to players; its presenter regression preserves the LAN, Invite, address and voice behavior. Check its on-screen wrapping and visibility before enabling production activity. All three show the approved section "When a player hosts a public Internet session" of `MultiplayerPrivacyText.md` word for word, and each path's test checks it against that document; the address and voice wording is unchanged. Existing downloaded copies of earlier public data cannot be recalled. Deployment and live verification remain separate release gates.

The existing hourly relay-spend cron remains separate from five-minute activity collection. Durable Object migration identities stay unchanged; these are internal SQLite table upgrades. No deployment credentials belong on the public page.

## Author and player experience

Mod authors add no telemetry or boilerplate. The CLI, launcher and native Public HOST show the activity notice before starting or opening a public game; choosing invite-only keeps their session out of public activity. The status page shows inclusive public bands, withheld samples and genuine gaps. Hide my IP and voice consent are unchanged.
