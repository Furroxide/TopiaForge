# Cloudflare deployment host

The Worker source stays in the private `Furroxide/TopiaForge-Status` repository. Its GitHub plan cannot enforce required reviewers on a private repository. The public `Furroxide/TopiaForge` repository hosts the manually dispatched, reviewer-gated [`Deploy Cloudflare services from Status source`](../../.github/workflows/deploy-private-status-source.yml) workflow. The workflow accepts only a full commit SHA that is still the tip of Status `main`; a protected environment releases credentials after review. This deploys services only. It does not publish a TopiaForge client release or turn on production features.

**Cutover state, 2026-11-17:** The target zone and registrar registration are active, all three public Worker domains are attached, and target Status D1 has migrations `0001` through `0003`. Staging monitoring is active. The target production Worker remains feature-locked, and the source Workers remain paused. The [initial cutover sequence](#initial-target-account-cutover-completed) below records the migration; do not repeat its pre-migration D1 or registrar steps during routine updates. For later service updates, review the exact current Status `main` revision and any new SQL, dispatch only the affected target through the protected workflow, and verify the public route and feature state afterward.

## Protected environment secrets

Configure these in TopiaForge, never in a checkout or command line:

| Environment | Secrets |
| --- | --- |
| `control-plane-staging` | `STATUS_REPO_READ_TOKEN`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `ANALYTICS_API_TOKEN` |
| `control-plane-production` | `STATUS_REPO_READ_TOKEN`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `STATUS_CLOUDFLARE_API_TOKEN`, `STATUS_DATABASE_ID`, `STATUS_INGEST_TOKEN_STAGING`, `SERVICE_KEY`, `ADMIN_TOKEN`, `TURN_KEY_ID`, `TURN_KEY_API_TOKEN`, `ANALYTICS_API_TOKEN` |

`STATUS_REPO_READ_TOKEN` is a fine-grained GitHub token with **Contents: read** only on `TopiaForge-Status`. Store it separately in both protected environments; do not make it a repository secret. The staging and production Cloudflare tokens need Individual Workers Editor on only their respective existing Workers. The status token needs Individual Workers Editor on `topiaforge-status` and D1 Write for its existing database. Both `CLOUDFLARE_ACCOUNT_ID` secrets must identify the target account. Enter tokens and IDs through the provider secret forms. A token value is not recoverable from Cloudflare after creation; rotate a lost token instead of looking for it in logs.

The preflight requires staging's exact `dev`/`main` branch allowlist and production's main-only branch rule. It rejects a missing reviewer, a wrong branch or repository, and an unrecognized target before the deploy job names an environment. The existing production environment prevents self-review but currently permits administrator bypass. Use that bypass only after a separate recorded review of the exact source revision and deployment plan, as the control-plane runbook requires. Keep the environment and its reviewers in place; do not bypass the preflight to deploy.

The status deploy uploads `STATUS_INGEST_TOKEN_STAGING` as the Worker's `INGEST_TOKEN_STAGING` alongside the reviewed code. The protected workflow's `retire_legacy_bindings` option removes the obsolete migration binding from each Worker and the unused production ingest binding from Status. Put the same newly generated staging ingest value in the protected `control-plane-production` environment and the staging monitor's `STATUS_INGEST_TOKEN` secret before starting authenticated probes. Do not configure production monitor secrets at this stage. The control-plane deploy passes a temporary, private secrets file to Wrangler so code and credential changes are released in the same protected job. It always sets `ANALYTICS_ACCOUNT_ID` from that environment's target `CLOUDFLARE_ACCOUNT_ID` and requires an `ANALYTICS_API_TOKEN` with Account Analytics Read on the target account. Production additionally requires `SERVICE_KEY` (32–64 random bytes, unpadded base64url), `ADMIN_TOKEN` (at least 32 random characters), and the target production TURN key's ID and one-time API token. Keep each environment's service, admin and TURN credentials separate; a target-account analytics read token can serve both. Enter values only in the protected GitHub environment secret forms. The temporary files are removed at the end of their deploy steps; existing Worker secrets omitted from them remain in Cloudflare. The Cloudflare dashboard's **Add variable and deploy** control directly publishes a Worker version, so it is outside this production deployment path.

2. Confirm source and target data, Worker bindings, secrets, DNS records, redirect rules, TLS settings, and a durable source D1 export outside either repository. The target account must have Workers Paid before serving production traffic. 3. From TopiaForge `main`, dispatch the workflow once per target: `status`, `control-plane-staging`, then `control-plane-production`. Supply the same reviewed 40-character Status `main` SHA and leave `verify_public_routes` false while the target zone is inactive. 4. Confirm each target deployment succeeded and its bindings still point to the intended target account resources. Keep production feature flags off. Confirm the target zone's existing non-Worker DNS records, apex redirect, and Full TLS mode match the source. Check that DNSSEC is off before the Registrar move. Record the target zone's assigned nameserver pair; Cloudflare requires an active zone before adding Worker Custom Domains.
5. Accept the pending Cloudflare Registrar account move in the target account. Verify that registry delegation matches the target zone's assigned nameservers, use the zone Overview **Re-check now** control, and wait until the target zone is **Active** and its edge certificate is ready. A registration move does not carry the source zone's configuration. Attach `mp-staging.topiaforge.dev`, `mp.topiaforge.dev`, and `status.topiaforge.dev` as Custom Domains to their corresponding target Workers. Review this domain transfer and the brief routing transition at action time.
6. Dispatch again with `verify_public_routes` true, or perform the same public smoke checks: both `/v1/status` endpoints return `topiaforge.control-plane-status/1`, production reports `hosting`, `invites`, `signaling`, and `relay` all `false`, `/api/status` returns `topiaforge.public-status/1`, staging history has five components, and unauthenticated internal status writes return 401. Check the status page in a browser and confirm the migration 503 has gone.
7. Run an authenticated staging basic and full monitor probe and read the new observation from target D1. Run the control-plane live check for an invite-only host, signaling, and two real TURN relays; confirm the Worker reports the intended provider and analytics configuration. Verify the target staging Worker already has its other required secrets; this workflow synchronizes its target analytics account ID and token. Keep production monitor secrets absent until the public activity text is on TopiaForge `main` with status schema version 2. Keep production features off until their release decision.
8. After live checks and a rollback window, rotate or revoke obsolete source-account deployment tokens, retire temporary migration capabilities, and remove old resources through a separately reviewed cleanup. Only then review downgrading the old account's Workers plan. Keep `production.launched` and `stableClientPublished` off until their release decisions.

The source and target accounts must not both accept production writes. If a target deployment or domain transfer fails, stop and inspect the state before changing either write barrier or DNS again. The private Status repository still lacks branch protection; review the exact Status commit independently before approving a deployment.
