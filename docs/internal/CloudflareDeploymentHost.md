# Cloudflare deployment host

The Worker source stays in the private `Furroxide/TopiaForge-Status` repository. Its GitHub plan cannot enforce required reviewers on a private repository. The public `Furroxide/TopiaForge` repository hosts the manually dispatched, reviewer-gated [`Deploy Cloudflare services from Status source`](../../.github/workflows/deploy-private-status-source.yml) workflow. The workflow accepts only a full commit SHA that is still the tip of Status `main`; a protected environment releases credentials after review. This deploys services only. It does not publish a TopiaForge client release or turn on production features.

## Protected environment secrets

Configure these in TopiaForge, never in a checkout or command line:

| Environment | Secrets |
| --- | --- |
| `control-plane-staging` | `STATUS_REPO_READ_TOKEN`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` |
| `control-plane-production` | `STATUS_REPO_READ_TOKEN`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `STATUS_CLOUDFLARE_API_TOKEN`, `STATUS_DATABASE_ID` |

`STATUS_REPO_READ_TOKEN` is a fine-grained GitHub token with **Contents: read** only on `TopiaForge-Status`. Store it separately in both protected environments; do not make it a repository secret. The staging and production Cloudflare tokens need Individual Workers Editor on only their respective existing Workers. The status token needs Individual Workers Editor on `topiaforge-status` and D1 Write for its existing database. Both `CLOUDFLARE_ACCOUNT_ID` secrets must identify the target account. Enter tokens and IDs through the provider secret forms. A token value is not recoverable from Cloudflare after creation; rotate a lost token instead of looking for it in logs.

The preflight requires staging's exact `dev`/`main` branch allowlist and production's main-only branch rule. It rejects a missing reviewer, a wrong branch or repository, and an unrecognized target before the deploy job names an environment. The existing production environment prevents self-review but currently permits administrator bypass. Use that bypass only after a separate recorded review of the exact source revision and deployment plan, as the control-plane runbook requires. Keep the environment and its reviewers in place; do not bypass the preflight to deploy.

## Target account cutover

1. Review the exact Status `main` SHA and the pending D1 migration before dispatch. Migration `0003_public_activity.sql` deletes old combined activity rows, blocks legacy writes, and creates public-only storage. Its SHA-256 is `514a6f4deef1303f83887a81e38d1c28525e06b5b1ab7d84819b4d24c0f99e51`. Remote D1 writes require approval of its exact SQL statements under `RULES.md`; enter this hash as `migration_sql_sha256` only after that approval. The workflow refuses additional SQL migration files until they receive separate review.
2. Confirm source and target data, Worker bindings, secrets, DNS records, redirect rules, TLS settings, and a durable source D1 export outside either repository. The target account must have Workers Paid before serving production traffic. Confirm that target D1 records exactly `0001_status.sql` and `0002_claim_owners.sql` in `d1_migrations`; otherwise the deployment would apply more than the approved SQL. Keep the source write barrier closed. The target Workers need clean source deployments to replace their temporary migration bridges before receiving public traffic.
3. From TopiaForge `main`, dispatch the workflow once per target: `status`, `control-plane-staging`, then `control-plane-production`. Supply the same reviewed 40-character Status `main` SHA and leave `verify_public_routes` false while the target zone is inactive. The status dispatch applies only pending migrations to the target D1 database. Deploy the status consumer and schema before the control-plane activity producer.
4. Confirm each target deployment succeeded and its bindings still point to the intended target account resources. Keep production feature flags off. Confirm the target zone's existing non-Worker DNS records, apex redirect, and Full TLS mode match the source. Check that DNSSEC is off before the Registrar move. Record the target zone's assigned nameserver pair; Cloudflare requires an active zone before adding Worker Custom Domains.
5. Accept the pending Cloudflare Registrar account move in the target account. Verify that registry delegation matches the target zone's assigned nameservers, use the zone Overview **Re-check now** control, and wait until the target zone is **Active** and its edge certificate is ready. Cloudflare Registrar does not provide the ordinary registrar nameserver edit; if delegation does not match, stop and use Cloudflare Registrar support before attaching Workers. A registration move does not carry the source zone's configuration. Attach `mp-staging.topiaforge.dev`, `mp.topiaforge.dev`, and `status.topiaforge.dev` as Custom Domains to their corresponding target Workers. Review this domain transfer and the brief routing transition at action time.
6. Dispatch again with `verify_public_routes` true, or perform the same public smoke checks: both `/v1/status` endpoints return `topiaforge.control-plane-status/1`, `/api/status` returns `topiaforge.public-status/1`, staging history has five components, and unauthenticated internal status writes return 401. Check the status page in a browser and confirm the migration 503 has gone.
7. Run an authenticated staging basic and full monitor probe and read the new observation from target D1. Run the control-plane live check for an invite-only host, signaling, and two real TURN relays; confirm the Worker reports the intended provider and analytics configuration. Keep production monitor secrets absent until the public activity text is on TopiaForge `main` with status schema version 2. Keep production features off until their release decision.
8. After live checks and a rollback window, rotate or revoke obsolete source-account deployment tokens, retire temporary migration capabilities, and remove old resources through a separately reviewed cleanup. Only then review downgrading the old account's Workers plan. Keep `production.launched` and `stableClientPublished` off until their release decisions.

The source and target accounts must not both accept production writes. If a target deployment or domain transfer fails, stop and inspect the state before changing either write barrier or DNS again. The private Status repository still lacks branch protection; review the exact Status commit independently before approving a deployment.
